# Plan: aws-anchor-publisher-and-scram-verifier

Issues: `#940` (publisher on AWS; widened to the audit-chain verify worker, user decision),
`#941` (no cleartext role passwords on the wire). Branch
`feat/aws-anchor-publisher-and-scram-verifier`, base `origin/main` 3383b3fcb.
Revision 1.

## Project context

- Type: `mixed` (web app + workers + operator scripts + Terraform). Tests: unit + real-PostgreSQL
  integration + CI.
- Verification environment constraints:
  - E1 — no AWS environment runs (the account is idle). Terraform is checked with `terraform fmt
    -check` and `terraform validate` only; nothing is planned or applied. The ECS wiring is
    `blocked-deferred` until the next AWS bootstrap; cost-justification: standing up the stack
    for this change costs more than the change, and every value the tasks read is checked
    locally (env schema, bundle boot) instead.
  - E2 — no RDS. The SCRAM change is verified on local PostgreSQL 16, which accepts a
    pre-computed verifier exactly as RDS PostgreSQL does (the server feature, not an RDS one).

## Objective

1. Run the audit-anchor publisher and the audit-chain verify worker on AWS, as the outbox and
   retention-GC workers already run. Today production validation requires
   `AUDIT_ANCHOR_PUBLISHER_ENABLED=true`, yet no task publishes, and no deployment of any kind
   runs the verify worker.
2. Stop sending role passwords in cleartext: a refused `CREATE/ALTER ROLE … PASSWORD` is logged
   in full under the default `log_min_error_statement = error`. Send a SCRAM-SHA-256 verifier
   instead, as psql's `\password` does (`PQencryptPasswordConn`).

## Contracts

### C1 — worker bundles
- The member set "long-running worker entrypoints" is derived by
  `ls scripts/*-worker.ts scripts/*-publisher.ts`: `audit-outbox-worker`, `retention-gc-worker`,
  `audit-chain-verify-worker`, `audit-anchor-publisher`. The Dockerfile bundles and copies all four
  into `dist/` with the same esbuild flags as the existing two.
- `npm run worker:audit-anchor-publisher` (`tsx scripts/audit-anchor-publisher.ts`) joins the
  existing `worker:*` scripts.
- `scripts/checks/check-worker-bundle-smoke.sh` currently extracts only
  `npx esbuild scripts/.*-worker\.ts`, so a publisher bundle would ship unsmoked. Its extraction
  covers every esbuild invocation that writes to `dist/`, and it fails if the set of bundles it
  boots differs from the Dockerfile's `COPY … /app/dist/*.js` lines.
- `audit-chain-verify-worker` gains `--validate-env-only` (exit 0 after module load and config
  parse, before any DB connection), matching the others, so the smoke can boot it.
- Control class: fail-closed verification gate (pre-pr + CI). Adjudication: Node actually loading
  the CJS bundle.

### C2 — ECS tasks and services (Terraform)
- Two task definitions and services, mirroring the existing workers (same image, `skip_destroy`,
  `worker_cpu/memory`, private subnets, circuit breaker, `ignore_changes = [task_definition]`,
  `desired_count = var.worker_desired_count`), each with its own log group, `RunningTaskCount`
  alarm and outputs (service name, task-definition ARN).
- Publisher container: `command = ["node", "dist/audit-anchor-publisher.js"]`; environment
  `AUDIT_ANCHOR_PUBLISHER_ENABLED=true` and, when `var.enable_s3_audit_anchors`,
  `AUDIT_ANCHOR_DESTINATION_S3_BUCKET`; secrets `AUDIT_ANCHOR_PUBLISHER_DATABASE_URL`,
  `AUDIT_ANCHOR_SIGNING_KEY`, `AUDIT_ANCHOR_TAG_SECRET`, `DEPLOYMENT_ID` from the app secret. No
  `DATABASE_URL`: the publisher falls back to it, and handing it the app role would hide a
  missing least-privilege URL.
- Verify-worker container: `command = ["node", "dist/audit-chain-verify-worker.js"]`; secret
  `AUDIT_CHAIN_VERIFY_DATABASE_URL` mapped from the app secret's `DATABASE_URL` key (role
  `passwd_app`, user decision: no new role; the worker's reads are already proven as
  `passwd_app` by `audit-chain-verify-worker-rls.integration.test.ts`).
- `DEPLOYMENT_ID` is a new app-secret key (a UUID generated once per deployment; the publisher
  refuses to run when it differs from the one stored in `system_settings`). Documented with the
  other keys; generated by `uuidgen`, never rotated.
- S3: the publisher uses the existing `ecs_audit_anchor_s3` policy on the shared task role (PUT,
  GET, LIST; no DELETE). See SC2.
- When `var.enable_s3_audit_anchors = false` the publisher has no destination and exits fatally
  at boot (the circuit breaker stops it), the same loud failure the app task already has there.
- `scripts/deploy.sh` advances and rolls back all six services; `deploy-rollback.test.mjs` names
  them.
- Control class: N/A (deployment wiring). Acceptance: `terraform fmt -check`, `terraform
  validate` (E1); the deploy script test; every secret key a task names is listed in the
  README/AWS setup docs (checked by a grep in the test plan, not a gate).

### C3 — SCRAM verifier helper
- `scripts/lib/scram-verifier.mjs` exports `scramSha256Verifier(password, opts?)` → string
  `SCRAM-SHA-256$<iter>:<b64 salt>$<b64 StoredKey>:<b64 ServerKey>`, the format PostgreSQL stores
  in `pg_authid.rolpassword`. Defaults: 4096 iterations, 16-byte random salt (PostgreSQL's
  `scram_iterations` / `SCRAM_DEFAULT_SALT_LEN`). Built only from `node:crypto` `pbkdf2Sync`,
  `createHmac`, `createHash` per RFC 5802 §3 (SaltedPassword, ClientKey, StoredKey, ServerKey);
  no new primitive.
- The password is passed through SASLprep only as PostgreSQL does: our passwords are generated
  ASCII; non-ASCII input is refused with an error rather than normalised differently from the
  server (the server applies SASLprep and falls back to the raw bytes when it fails, so an
  un-prepped non-ASCII password could store a verifier the client cannot log in with).
- Invoked as a CLI (`node scripts/lib/scram-verifier.mjs`) it reads the password from stdin and
  prints the verifier, for the shell scripts in C4.
- Not exported anywhere under `src/`; it is an operator-tooling helper.

### C4 — every operator path sends the verifier
- Member set, derived by `git grep -n "PASSWORD '" -- scripts ':!*.test.*'` plus
  `convergeRole`/`createRole` in `bootstrap-rds-roles.mjs`: `bootstrap-rds-roles.mjs` (CREATE
  and ALTER), `set-outbox-worker-password.sh`, `set-retention-gc-worker-password.sh`,
  `set-audit-anchor-publisher-password.sh`. Each sends `PASSWORD '<verifier>'`.
- Out of the class: `infra/postgres/initdb/*.sql` and the CI workflows set fixed dev/CI
  passwords on throwaway databases (SC3).
- Forbidden pattern: `escapeLiteral\((password|pw)\)` in `bootstrap-rds-roles.mjs` — reason: the
  cleartext must not reach the statement. In the shell scripts the statement is built only from
  the helper's output.
- The `bootstrap-rds-roles.mjs` header and `#941`'s residual note change: a refused statement
  now logs a verifier of a random secret, which is what `\password` exposes.
- The image ships `scripts/lib/scram-verifier.mjs` beside `bootstrap-rds-roles.mjs` (it runs
  from the image on RDS); `check-mjs-imports.mjs` already derives image assets from imports.
- Control class: N/A (removes an exposure). Acceptance in the testing strategy.

## Testing strategy

- C3 unit (`scripts/__tests__/scram-verifier.test.mjs`):
  - RFC 7677 §3 vector: password `pencil`, salt `W22ZaJ0SNY7soEsUEjb6gQ==`, 4096 iterations →
    the keys the helper derives reproduce the RFC's `ServerSignature`
    (`6rriTRBi23WpRR/wtup+mMhUZUn/dB5nLTJRsjl95G4=`) for the RFC's AuthMessage. Red proof: swap
    "Server Key" and "Client Key" → red.
  - format: four fields, decodable base64, salt 16 bytes, keys 32 bytes; two calls differ (salt
    is random); non-ASCII refused.
- C3 integration, cross-implementation (superuser, throwaway role): set a cleartext password,
  read `rolpassword`, parse its salt and iterations, recompute with the helper → identical
  string. Proves the helper matches the server's own derivation, not only the RFC.
- C4 integration: the existing `bootstrap-rds-roles.integration.test.ts` cases that log in with
  the installed password (T2 rotated password, T5 quote/backslash/semicolon password) now run
  through the verifier path, so a wrong verifier fails login. Added: after `convergeRole`,
  `rolpassword` is a SCRAM verifier and the statement text sent contains no cleartext (captured
  through a client wrapper that records the SQL).
- C4 shell scripts: `set-*-password.test.mjs` DRY_RUN cases assert the printed statement carries
  a verifier, not the password. One live case per script is not added: they share the helper and
  the psql path is unchanged.
- C1: the bundle smoke boots all four bundles; red proof: drop the publisher's `COPY` → the
  smoke's Dockerfile-set comparison fails.
- C2: `terraform fmt -check`, `terraform validate` (E1); `deploy-rollback.test.mjs` with six
  services.

## Considerations & constraints

- SC1 — the verify worker and publisher in `docker-compose.workers.yml` and `infra/k8s/` (the
  same gap on the other deployment targets) — follow-up issue filed with the PR.
- SC2 — a dedicated task role for the publisher (today the anchor S3 policy sits on the role every
  task shares, app included) — follow-up issue; pre-existing, not widened here.
- SC3 — initdb and CI password statements (fixed non-secret values on throwaway databases).
- SC4 — CloudWatch metric filters on the verify worker's heartbeat/`CHAIN_VERIFY_FAILED`
  (alerts are documented for Datadog/Loki; AWS gets the `RunningTaskCount` alarm only) —
  follow-up issue.
- The verify worker as `passwd_app` reads every tenant's chain under named grants — the same
  reads the app's maintenance endpoint can make; no privilege added.

## User operation scenarios

- Operator bootstraps AWS: generates `DEPLOYMENT_ID` with `uuidgen`, adds it and
  `AUDIT_ANCHOR_PUBLISHER_DATABASE_URL` to the app secret, runs `bootstrap-rds-roles.mjs` (which
  now sends verifiers), applies Terraform, deploys; six services come up.
- Operator rotates the outbox worker password on self-hosted Docker:
  `set-outbox-worker-password.sh < <(openssl rand -hex 32)`; the server log of a refused statement
  would show a verifier only.
